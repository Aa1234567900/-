## 1. 产品概述（TL;DR）

安记是一个**非评判式、极低摩擦**的个人消费理解工具原型：帮用户"看见钱怎么被使用、并逐步理解为什么花、是否值得"，而不是用超支警告、羞耻感或储蓄施压去督促省钱。

核心承诺只有一句话：**不打分、不批评，先帮你看看钱花哪了。**

---

## 2. 背景与问题

1. **现有工具多为"评判 + 储蓄导向"**：预算 App 普遍用超支警告、排行榜、羞耻文案，引发焦虑，流失高。
2. **"看见"不等于"理解"**：用户能查到"花了多少钱"，却很少理解"为什么花、是否值得、连到了什么"。
3. **记录摩擦过高**：传统记账要选分类、写备注、对发票，单笔常超 30 秒，难以形成习惯。
4. **验证目标单一**：本产品第一目标不是"帮人省钱"，而是验证——**用户是否愿意以极低成本持续记录，并逐步理解自己的消费行为**。

---

## 3. 目标与成功指标

### 3.1 North Star（用户价值）
用户愿意以极低成本持续记录消费，并逐步理解自己的消费行为（即第 1 节的单一核心验证目标）。

### 3.2 Proxy Metric：周度"理解闭环率"（WULLR）
= 当周既完成 ≥1 笔记录、又主动打开 Insight 或补充 ≥1 个 Why 标签的 UV ÷ 当周活跃记录 UV。
**目标：第 4 周 ≥ 40%。**

### 3.3 护栏指标（须监控，非 North Star）
| 指标 | 目标 | 说明 |
|---|---|---|
| WAR-d（周活跃记录天数） | ≥ 3 天/周 | 习惯底线 |
| 单笔记录耗时中位数 | ≤ 5s | 低摩擦底线 |
| 负面情感反馈率 | 低于阈值（红） | "被评判/焦虑"关键词 |
| 提醒关闭率 | 不宜过高 | 过高说明打扰 |

## 4. 用户画像

- **核心用户**：想了解自己消费但不想被说教的人；对"预算/记账工具"有抵触；愿意用极低门槛尝试。
- **诉求**：快速记一笔 → 偶尔看看"钱怎么花" → 自行判断是否需要设目标。
- **非目标用户**：需要严格预算管控、投资管理、家庭共账的重度财务用户。

---

## 5. 用户故事（核心 Epic）

- **E1 极简记录**：作为用户，我希望 3–5 秒内完成一笔记录（金额→自动分类→一键完成），不必填 Why、不必设目标。
- **E2 初步理解**：作为用户，我希望在首页一眼看清"本月支出 + 分类分布 + 近 6 月趋势"，无需复杂洞察。
- **E3 后置理解**：作为用户，我希望在 Insight 里自愿给几笔补 Why Tag，并由规则生成一句非评判式总结。
- **E4 本地可用**：作为用户，我希望不登录也能用，数据存在本机、刷新/重启/离线都不丢。
- **E5 多端同步（可选）**：作为用户，我希望登录后数据同步到云端，换设备也能恢复；无网络时本地照常、恢复后补传。
- **E6 目标（可选）**：作为用户，我希望主动建立"本月想为 XX 存下多少"的目标，进度仅在开启后展示。
- **E7 安装即用（PWA）**：作为用户，我希望把站点"安装"到桌面/手机，像 App 一样离线打开。

## 7. 三大核心页面

### 7.1 Home — 我的钱怎么被使用
- **目的**：一眼看清"钱花在哪、怎么变的"，而非"为未来存了多少"。
- **布局**：顶部本月支出总览（金额 + 环比）→ 主区分类分布（环形/条形）+ 近 6 月趋势 → 可选目标进度模块（开启后出现）→ 次区最近记录列表。
- **约束**：文案中性；不出现"超支/为未来存下"等施压或储蓄导向表述。

### 7.2 Quick Log — 3–5 秒完成
- **目的**：把记录成本压到最低，形成习惯。
- **布局**：大数字键盘（默认弹出）→ 金额输入区 → 规则自动分类 chip（建议置顶，可改）→「记好了」。
- **约束**：金额输入后自动带出上次/同类分类；Why Tag / 目标不在此页，提供"稍后补充"入口后置到 Insight。

### 7.3 Insight — 理解消费模式
- **目的**：把"花了"变成"怎么花、为什么、连到哪（若用户有目标）"。
- **布局**：tab1 趋势（分类 + 月度环比）→ tab2 为什么（用户补充的 Why 分布，未补则温和引导）→ tab3 轻回顾（规则模板生成一句理解）→ 目标连接（可选）。
- **约束**：所有提问非评判；评分/标记不排名、不对外。

## 8. 数据模型

### 8.1 交易 Transaction（本地 + 云端同构）
| 字段 | 类型 | 说明 |
|---|---|---|
| id | string | 客户端生成唯一 ID（云端表主键为 user_id+client_id） |
| amount | number | 金额 |
| note | string | 备注（可选） |
| catKey | string | 规则分类键（默认 other），可手动改 |
| createdAt / updatedAt | number | 时间戳，用于云端 last-write-wins |
| whyTag | string? | 后置 Why 标签（可选，允许为空） |
| goal_id | string? | 关联目标（可选，允许为空） |

### 8.2 目标 Goal（每用户单例）
`{ targets: [], monthlyGoal: {monthKey, targetName, goalAmount, income, confirmedAmount, closed}, catTags: {}, rules: [] }`
- `monthlyGoal` 由用户月末**主动确认**计入金额，系统不自动把结余计入目标。

### 8.3 存储分布
- **本地（权威离线缓存）**：IndexedDB（对象仓库 `txns` 主键 `id`、`goals` 单例键 `singleton`）；不支持时降级 `localStorage`（键 `anjie_txn_v2`/`anjie_goal_v2`）。
- **云端（可选）**：SQLite `users` / `txns(user_id, client_id)` / `goals(user_id)`，按 `user_id` 行级隔离。

## 9. 技术架构与实现约束

### 9.1 总体
- 前端：原生 **HTML + CSS + JavaScript**，无框架、无构建步骤。
- 本地优先：数据先落 IndexedDB；云端为"可选增强"，不可达时不影响本地使用。

### 9.2 本地存储（`localdb.js`）
- 零依赖 IndexedDB 封装；`localStorage` 自动降级；首次新版自动迁移历史 localStorage 数据（幂等）。
- API：`getAllTxns / putTxns / clearTxns / getGoals / saveGoals / clearAll / migrateFromLocalStorage / isFallback`。

### 9.3 云端（可选，`server/`）
- **Node.js + Express + SQLite（better-sqlite3, WAL）**；JWT 鉴权（`jsonwebtoken` + `bcryptjs`）。
- Bearer 中间件把 `user_id` 挂到请求，所有查询按 `user_id` 隔离（行级安全）。
- 同源托管前端与 API，避免 CORS 与跨域存储问题。
- 接口：`/api/health`、`/api/auth/register`、`/api/auth/login`、`/api/txns`、`/api/txns/sync`、`/api/goals`。

### 9.4 同步策略
- 登录后 `save()` 增量推送（last-write-wins，按 `updatedAt` 覆盖；带 `_deleted` 标记则删除）。
- 本地为权威离线缓存；`pull()` 拉取后若云端为空账户，则把本地数据先上传（`seedFromCloud`），避免丢失。
- 顶栏常驻同步状态指示（`☁ 已同步 / ☁ 同步失败`），让用户一眼看到是否真的上云。

### 9.5 降级与容错（关键产品边界）
> ⚠️ 这是从真实 Bug 沉淀的产品要求：**前端绝不允许因后端缺失而崩溃。**

- 当页面来源没有后端（纯静态托管 / 离线）时，浏览器请求 `/api/*` 会被当成未知路径返回 HTML。
- `cloud.js` 的 `api()` 必须：先取文本再 `JSON.parse`，解析失败则抛**友好错误**（`云端返回了非 JSON 响应…请改用「仅本地使用」`），绝不抛 `Unexpected token '<'`。
- `fetch` 自身失败（后端不存在/网络不可达）也必须兜成友好错误（`无法连接云端…`）。
- 登录界面在加载时调用 `Cloud.checkBackend()` 检测 `/api/health`；不可达时显示**温和琥珀色提示**（非红色报错），引导用户走「仅本地使用」。

### 9.6 PWA
- `manifest.webmanifest`（standalone、品牌色、图标）+ `sw.js`（缓存应用壳，离线可开）+ `icons/`（192/512/maskable）。
- 仅 `http(s)` 生效；`file://` 下安装/离线不启用，但记账等核心功能仍可用。

## 10. 关键用户流程

### 10.1 Onboarding（无强制目标）
欢迎（"不打分、不批评，先看看钱怎么花"）→ 直接记一笔 / 轻量导入 →（可选）建 1 个目标或"先跳过" → 进入 Home。

### 10.2 每日记录（核心，3–5s）
打开 → 输入金额 → 系统带出分类建议 → 一键「记好了」→ 中性提示"记好了"。

### 10.3 理解（后置，非每日强制）
任意时刻打开 Insight → 自愿补 Why Tag → 规则生成一句理解。

### 10.4 本地 ↔ 云端同步
登录 → `pull()` 拉取（云端空则上传本地）→ 日常 `save()` 增量推 → 顶栏显示同步状态；离线时本地照常，恢复后下次 `save()` 补传。

### 10.5 无后端兜底流程
打开应用（静态托管，无后端）→ `checkBackend()` 返回 false → 登录界面显示温和提示 → 用户点「仅本地使用」→ 全程本地 IndexedDB 可用，数据留存。

## 11. 设计原则（不可突破）

**非评判 · 低摩擦 · 目标导向（连接未来而非节俭施压）· 用户自主权。**

不实现：登录之外的支付 / 社交 / 贷款 / 投资 / 理财推销 / 强制预算报警 / AI 基础记账 / 自动把结余计入目标 / 排名与对外曝光。

## 12. 核心假设与验证方法

| 假设 | 验证方法 | 成功 / 失败信号 |
|---|---|---|
| **H1** 用户愿以极低成本控制记录 | 埋点漏斗：耗时分布、WAR-d、D7/D30 留存 | 成功：单笔 ≤5s、WAR-d≥3、留存健康；失败：>10s 比例高或留存骤降 |
| **H2** 去掉强制 Why/目标后摩擦下降 | v0.1(强制) vs v0.2(可选) 完成率/放弃率 | 成功：完成率↑、放弃率↓ |
| **H3** 基础趋势即可初步理解 | Insight 访问率/补标率；Comprehension Test（"这月花最多的是哪类？"） | 成功：访问率/补标率随周↑、测试正确率↑ |
| **H4** 非评判语气不易引发焦虑 | 负面情感反馈率、提醒关闭率 | 成功：负面率低于阈值、关闭率低 |
| **H5** Rule-based 分类够用 | 人工抽样准确率、手动改分类比例 | 成功：达到可用性门槛、改分类率低 |
| **H6** 目标是"锦上添花"非门槛 | Onboarding 跳过比例、D14 主动建目标比例 | 成功：多数跳过但部分后续自建 |
| **H7（技术）** IndexedDB 持久化可靠 | 模拟刷新/重启后数据留存测试 | 成功：已通过自动化测试 |
| **H8（技术）** 无后端降级体验好 | 无后端时本地可用 + 温和提示，无崩溃 | 成功：已通过自动化测试（HTML/网络失败兜底） |

## 13. 边界与非目标（Won't，本期）

- 多账户聚合视图、复杂洞察、OCR、对话式查询。
- AI 基础记账（MVP 用 Rule-based）。
- 强制预算报警、社交排名、理财推销、投资/贷款/支付。
- 自动把"本月结余"计入目标（必须用户主动确认）。
